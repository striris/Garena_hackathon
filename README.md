# CINDERFALL

**An AI-directed strategy demo where player behaviour changes the opportunities on a fair battlefield.**

CINDERFALL is a short, playable single-player strategy prototype for the
**Garena AI Build Challenge 2026**. You lead the Ashfarers against the Saltkin
across two opposing routes around a living caldera. The game is deliberately
small enough to learn in one match, but its map can react to the *resolved*
state of play: resources shift, a passage opens, or a threatened area changes
the next decision for both sides.

The point is not to let an LLM secretly run a game. It is to demonstrate a
practical AI pattern for digital entertainment: **observe public play → compare
safe alternatives → select an explainable opportunity → validate it in code →
show the player a new, fair decision.**

## Why this problem

Small strategy games often face an awkward trade-off: fixed maps become
predictable, while scripted “rubber-band” events can feel arbitrary or unfair.
CINDERFALL explores a third option for designers and players:

| Player problem | CINDERFALL response |
|---|---|
| Repeated openings feel solved | A public `Ash Surge`, Beacon, and later world opportunities create a different shared focal point each seed. |
| Adaptation can feel like cheating | The system sees only settled public history, never the player’s current queued actions. |
| Dynamic events can remove agency | Every candidate is simulated, limited by hard guardrails, warned in advance, and revalidated before it executes. |
| A “smart AI” is hard to trust | The audit console exposes the source, latency, evidence, candidate set, fallback, and measured prediction. |

## What the prototype demonstrates

| Component | What it does |
|---|---|
| Playable game loop | Queue actions, resolve simultaneous orders, manage Supply, capture objectives, and win a complete match. |
| Adaptive rival | The Saltkin LLM selects a high-level Doctrine from resolved public behaviour; a deterministic bot turns it into legal orders. |
| Cinder world director | Trusted code generates safe resource/map opportunities and runs counterfactual rollouts; the LLM may select only one offered candidate ID. |
| Fairness layer | Hard limits protect capitals, reachable routes, minimum land, choice space, and repeated targeting. |
| Explainability | The game records what changed and why; the Cinder Console exposes technical evidence for a demo reviewer. |
| Resilience | Missing keys, timeouts, invalid JSON, or unsafe choices lead to a visible deterministic fallback, never a stalled game. |
| Mock player | A test control asks the configured LLM for an Ashfarer doctrine, then displays the legal queue generated by the same rules. |

## Quick start

Requirements: **Python 3.9+**. Node.js is optional and used only for offline
simulation. An API key is needed only for live LLM decisions; the deterministic
game remains playable without one.

```bash
python -m venv .venv
# macOS / Linux
source .venv/bin/activate
# Windows PowerShell: .\.venv\Scripts\Activate.ps1

python -m pip install -r requirements.txt
cp .env.example .env
# Windows PowerShell: Copy-Item .env.example .env
```

Set a newly issued key in `.env` (never commit this file):

```dotenv
CINDERFALL_API_KEY=your-new-key
CINDERFALL_AI_BASE_URL=https://api.siliconflow.cn/v1
CINDERFALL_AI_MODEL=moonshotai/Kimi-K2.7-Code
CINDERFALL_AI_TIMEOUT_SECONDS=15
CINDERFALL_HOST=127.0.0.1
CINDERFALL_PORT=8000
```

Run the local prototype:

```bash
python server.py
```

Open <http://127.0.0.1:8000>. The key stays in the Python process and is never
sent to the browser. Opening `index.html` directly works for offline rules, but
live AI endpoints require the local server.

## First-match guide

The game board and UI are bilingual. The fixed first line in the battle feed
always states the next useful player task; the log below it scrolls separately.

1. **Choose a route.** Click a glowing legal square on North or South to queue
   `1 · Expand`. Your first territorial order commits your main effort for two
   turns, so the other route is temporarily unavailable for active orders.
2. **Use a simple action.** `2 · Fortify` raises one supplied friendly square;
   `3 · Raid` attacks an adjacent enemy square; `4 · Combo` is available only
   when its displayed prerequisite is met. Keyboard `1–4` selects these tools;
   `Enter` resolves the turn; `Esc` clears the queue.
3. **Read the map.** A dashed glow means a legal target. `◇ Relay` is a
   two-square supply junction: taking both squares can cut the opposing front
   off from its capital. `★ Beacon` scores only while it has Supply.
4. **Watch for opportunities.** After the board has meaningfully developed,
   Cinder may warn about a safe change—such as a resource opportunity or a
   temporary central crossing. Both factions can use it under the same rules.

### Rules at a glance

| Action | Supply | Result |
|---|---:|---|
| `1 · Expand` | 3 | Claim an adjacent empty land square at strength 1. |
| `2 · Fortify` | 2 | Add 1 strength to a supplied friendly square, once per turn, maximum strength 6. |
| `3 · Raid` | 1 | Attack an adjacent enemy square. Two supplied directions against the same target gain +2 power. |
| `4 · Combo` | 2 | Optional support: a chained Expand starts its second square at strength 2, or a coordinated Raid gains +1. |

- `Expand`, `Fortify`, and `Raid` share action slots: **3 / 4 / 4 / 5 / 5 / 6**
  by turn, then stay at 6.
- Supply comes from connected owned terrain. Unused current Supply becomes
  Reserve, up to 8; Reserve is spent after current income.
- The two permanent cross-caldera bridges are flanking connections, not a third
  main route. Use them to enter the rear of the other front after a breakthrough.
- Seeded terrain keeps both sides rotationally symmetric. The opening `Ash
  Surge` grants `+1` fertility to supplied non-capital land on the shared focus
  route for four turns; total starting Supply may vary by seed but remains equal.
- Win with **10 supplied Beacon points**, or with the most land after **25
  resolved turns**.

## How the AI is real, bounded, and useful

```text
settled public play ──> aggregate player profile ──> Saltkin Doctrine LLM
                                                           │
                                                           v
                                               deterministic legal order bot

settled board ──> safe event candidates ──> counterfactual rollouts ──> Cinder LLM
                                                                         │ candidate ID only
                                                                         v
                                             live validation ──> warning ──> execution
```

### Saltkin: adapts without hidden information

The Saltkin model chooses only a Doctrine—stance, objective, target region,
risk, and a short observable rationale. It receives aggregate features such as
resolved Beacon focus, route preference, supply neglect, and warning response.
It cannot see the player’s current unsubmitted queue, select tiles, spend
Supply, or make an illegal attack.

### Cinder: changes opportunity, not outcomes

For each world beat, deterministic code enumerates template × intensity ×
region candidates, rejects unsafe choices, and simulates several short futures.
The model sees only aggregate rollout results and can return only an offered
candidate ID. The chosen candidate is checked again against the live board.

No event may destroy a capital, remove too much land at once, push a side below
three squares, repeatedly target one side, repeat the last template, sever all
routes, or remove more than 40% of either side’s immediately available
Expand/Raid choices. A timeout or malformed response uses an explicit safe
fallback.

See [AI_ARCHITECTURE.md](AI_ARCHITECTURE.md) for the authority boundary and
[THIRD_PARTY.md](THIRD_PARTY.md) for model, API, privacy, and license disclosure.

## Reviewer demo path (about five minutes)

1. Start a new ring and show the highlighted shared route, fixed task prompt,
   and legal-target glow.
2. Queue an Expand, explain the two-turn route commitment, then show Fortify or
   Raid with the `1–4` controls.
3. Use the `CINDER` tab to show the public player profile, a candidate set, the
   shadow baseline, and the safety checks.
4. Let Cinder create or warn about a new opportunity, then show that both sides
   can contest it under unchanged rules.
5. Press **Mock LLM Move** to display an LLM-selected doctrine and the
   deterministic legal Ashfarer queue it produces.
6. Toggle the failure simulation: after the short timeout, the game continues
   with a labelled fallback instead of pretending that a model response arrived.

## API and project layout

The local Python service exposes:

- `GET /api/ai/health`
- `POST /api/ai/saltkin`
- `POST /api/ai/director`
- `POST /api/ai/mock-player`

```text
ai/prompts/          versioned LLM prompts
ai/schemas/          strict response schemas
ai_service.py        OpenAI-compatible client and trusted validation
server.py            same-origin static/API service
js/engine.js         deterministic turn, Supply, combat, and victory rules
js/mapgen.js         symmetric routes, Relays, bridges, Beacon, opening focus
js/events.js         world event templates
js/validator.js      hard fairness guardrails
js/profile.js        resolved-history player profile and five-match memory
js/bot.js            legal deterministic order generator
js/director.js       candidate generation, rollouts, shadow baseline, LLM mapping
js/main.js           UI lifecycle, fallbacks, guide, and audit console
tools/simulate.js    offline balance and invariant checks
tests/               service, security boundary, and interaction tests
```

## Verification

Offline checks do not call a model or incur API cost:

```bash
node tools/simulate.js 100
python -m unittest discover -s tests -v
```

The simulator checks deterministic replay, rotational symmetry, bridges,
Relay supply cuts, command and budget limits, combat combos, Beacon scoring,
temporary crossings, all event templates, candidate safety, and AI privacy
boundaries. The test suite also verifies API failure handling, static-server
allowlisting, and UI interaction constraints.

## Scope and privacy

This is a demonstration prototype, not a production service. It intentionally
omits accounts, multiplayer networking, analytics, advertising, and persistent
personal data. The only retained player model is aggregate gameplay behaviour
in browser `localStorage` (at most five summaries), and it can be cleared from
the Cinder Console. The repository contains no API key.
